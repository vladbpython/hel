## [2.1.0]

### Note

The pool already scaled the number of consumers up and down by how full the
channels were on average. That signal cannot see skew: one hot shard among many
idle ones barely moves the average, so a hotspot never triggered anything, and
even when it did, adding consumers could not help. A shard has exactly one owner
at a time, which is what keeps the order of each key, so putting more workers in
the pool never puts more of them on the one shard that is actually busy.

This release adds a second, separate axis. The old axis still answers how many
consumers to run. The new one answers which consumer drains which shard. A hot
shard now gets a consumer of its own, while the cold shards are packed onto the
rest. Nothing about ordering, ownership, or the zero loss guarantee changes, and
on an even load the placement is exactly the same shard % active mapping as
before. The new behaviour only shows up when the load is truly skewed.

### Added

- **Load aware shard placement (hotspot isolation).** The monitor now reads the
  queue depth of every shard, not just the average. A shard whose fill crosses
  `hotspot_fill` counts as a hotspot and gets a consumer of its own, and the rest
  of the shards are spread over the other consumers by a greedy placement that
  fills the least loaded worker first. The chosen owners live in a per shard
  `desired` table that the worker loop reads when it claims a shard. K hot shards
  pull the active consumer count up to K + 1 (one per hotspot, plus one to drain
  the rest), capped by `max_consumers`, and each hot shard lands on a consumer of
  its own. Because moving a shard to another consumer still goes through the owner
  CAS (the old owner releases before the new one claims), the order of each key
  holds across every rebalance, exactly as it already did across a plain resize.

- **Three `Config` knobs for the new axis.** All have defaults that reproduce the
  previous behaviour on an even load, and all are set through the existing
  builder:

  ```rust
  Config::new(min, max)
      .hotspot_fill(0.80)        // per shard fill that marks a shard hot
      .rebalance_margin(0.15)    // how much lighter a worker must be to take a shard, as a fraction of CAP
      .hotspot_isolation(true)   // master switch for the whole placement axis
  ```

  - `hotspot_fill` is a per shard threshold, kept apart from the average
    `scale_up_fill` on purpose. One full shard among eight averages to 0.125, so
    `scale_up_fill` never fires on it, while `hotspot_fill` looks at that one
    shard and does. Same units, different quantity.
  - `rebalance_margin` keeps placement steady. A shard moves to another consumer
    only when that consumer is at least `rebalance_margin * CAP` items lighter, so
    small wiggles in load do not reshuffle owners and tail latency stays calm. 0.0
    reacts fastest and thrashes most; a larger value is calmer but reacts to a new
    hotspot a little slower.
  - `hotspot_isolation(false)` turns the placement axis off and goes back to the
    plain shard % active mapping.

- **Cooperative yield on the async idle path.** An idle async worker used to spin
  with `std::thread::yield_now`, which does not hand the runtime thread back to
  other tasks and starves them whenever `max_consumers` is larger than the number
  of runtime threads. Idle async workers now yield in a way the runtime
  understands (a small `YieldNow` future that works on any runtime and returns
  `Pending` once), so a pool with more consumers than threads no longer lets one
  idle worker keep a thread to itself. The sync path is unchanged. Under load the
  idle path is never entered, so throughput is untouched.

- **Tests for the new behaviour.** Placement is covered by unit tests: an even or
  idle load reproduces the shard % active mapping exactly, a single hot shard is
  isolated with the other shards moved off its worker, a shrunk pool never targets
  a retired worker, and the `rebalance_margin` band stops churn while a real gap
  still moves an owner. A comparison test (`old_vs_new_on_one_hot_shard`) prints,
  side by side, the old average fill monitor leaving a hot shard sharing a
  consumer versus the new one isolating it at the same consumer count. The loom
  shard ownership models still pass unchanged.

- **Zero-loss benchmark under injected panics.** The new `zero_loss_faults`
  benchmark in `pool_scaling.rs` panics the handler on one item in every K and
  checks, on every run, that the counts add up to N and that the checksum of the
  item values in both buckets matches, so nothing is lost and nothing is handled
  twice. Running it is also a stress test of the guarantee, because any violation
  fails the run. Measured on an Apple M2 Max with 50000 items, the split is exact
  at every rate (for example 1 in 3 gives 33333 processed and 16667 dead
  lettered, total 50000), and throughput degrades smoothly with the fault rate
  rather than falling off a cliff: sync goes from about 4.85 to 1.62 Melem/s and
  async from about 2.91 to 1.20 Melem/s as the panic rate rises from 0.1 percent
  to 33 percent. The drop is the cost of unwinding and routing a failed item to
  the dead-letter sink, not a weakening of the guarantee.

### Performance

- **The new logic lives entirely in the monitor** (one pass every
  `sample_interval`, 100 ms by default). The worker hot path is unchanged: it
  reads the same `desired` table it would have computed from the modulo rule. So
  there is no throughput cost on the draining path.
- **Placement scales with shard count.** Measured on an Apple M2 Max with 8
  consumers, across sync and async and all three routings (round robin, shard key,
  shard group), throughput stays flat as the shard count grows from 8 to 1024:
  about 4.1 to 4.9 Melem/s on sync and about 2.9 Melem/s on async, with no
  downward trend (async gives up at most about 5 percent at 1024 shards, inside
  the run to run noise). The same flat shape held on a 12 core machine. Scanning
  the shards once per pass is not a bottleneck at these sizes, so no owned shard
  index was added. The `shard_scaling_sync` and `shard_scaling_async` benchmarks
  in `pool_scaling.rs` cover this sweep.

### Compatibility

- No breaking changes to behaviour. `Config::new(...)` and every existing pool
  constructor and call site work unchanged, and the new fields have defaults that
  keep the old behaviour.
- Behaviour changes only under a skewed load, and can be turned off with
  `hotspot_isolation(false)`.
- `Config` is now marked `#[non_exhaustive]`. Build it through `Config::new(...)`
  and the builder methods (`.hotspot_fill(...)` and so on). Code outside the crate
  can no longer build a `Config` with a struct literal, so new fields can be added
  in future minor releases without breaking anyone.

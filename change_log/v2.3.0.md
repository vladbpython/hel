## [2.3.0]

### Added

- **Missing methods in SPSC wrappers.** `SpscSender` and `SpscReceiver` (wrappers,
  adding the shard number to errors) were not able to do everything that half of the channel can do, and they had to be avoided.
  Added `send_timeout`,
  `send_batch_timeout`, `send_batch_async` at the sender and `recv_timeout`,
  `recv_batch_timeout`, at the recipient. The set now matches
  completely, parity is secured by the test.
- **`PanicReason::is_cancelled()`** dead letter receiver can now distinguish
  the handler fell (defect, worth recording in the log) we were turned off halfway
  (usually it is enough to return the element to the queue).

### Fixed

- **SPSC: data race from secure code.** Cloning the sender was you can’t,
  but you can pass a link to it in two threads; two simultaneous
  `try_send` gave undefined behavior (Miri: `Data race detected`).
  Now all SPSC sending and receiving methods take `&mut self` and such code will not compile.
  Migration:
  `let (mut tx, mut rx) = ch.take_pair(0).unwrap()` the compiler will specify each location.
  MPMC is not affected, its sender is multi-threaded and remains with `&self`, `Clone` and `Sync`.
 
- **Pool: panic before creating the future killed the worker.** `handle` returns
  future, and the code before its appearance was executed outside the interceptor: the worker died, the element was lost, the panic counter was silent,
  the remaining elements froze unprocessed.
  Now such a panic is caught on the same basis as a normal one, the element goes to `dead_letter`, the worker lives.

- **Pool: canceling the task was eating the element.** While the handler is waiting on `await`,
  the element is with the worker; canceling a task by runtime (for example, when stopping
  application) dropped it along with the frame neither in processed nor in `dead_letter`.
  The element is now returned via `dead_letter` with the attribute `is_cancelled()`.
 
- **Pool: shard closure was delayed by one pass** if the last batch
  came simultaneously with the closure of the channel. There were no losses, just unnecessary delay.

- **`try_recv_batch_any` could hang forever.** Method collect from all shards, 
  without waiting, the blocking technique called inside by mistake: 
  the first empty shard with a live sender stopped the call forever, 
  even when neighboring shards were full of data.
- **`send_batch_timeout` multiplied the timeout by the number of shards.** For each busy
  the shard received the full `d`, and a call on four shards could wait up to 4x `duration`.
  Now `duration` is the budget for the entire call, the deadline is counted once, 
  Each shard gets the remainder.

- **Quadratic packet sending under load.** Having hit a full shard,
  `send_batch_async` (in `shard_key` and `shard_group`) sent one element at a time and
each time he shifted the entire rest of the pack in memory. There's now a plus line inside
  reusable buffer for batch path, all operations cost by size
  sent piece, not the rest, and batch mode works on every call.
  The order within the key and the API have not changed.

- **`queued()` could say empty about a non-empty channel.** Two counters were read
  in such an order that the second had time to go ahead; the difference became
negative and trimmed to zero (approximately 7 cases per 100,000 reads).
  The pool monitoring looks at this, once every half a minute it saw an empty shard
  queue instead of busy and could have made the wrong scaling decision.
  Fixed by changing the order of readings.

- **Capacity check has been moved to the assembly stage.** `CAP` must be a degree
  twos and not less than 2; Previously, the violation crashed the program with a panic at startup,
  now `SpscShard::<u64, 3>::new(1)` simply doesn't build. Number of shards at
  this is any: SPSC does not hash anything, `new(6)` on six cores will create exactly
  six channels, without rounding anything.

- **SPSC: batch sending simplified.** Removed atomic comparison with exchange and
  repeat cycle, they are needed when several senders are fighting for slots, and
  in SPSC there is exactly one sender, and this is guaranteed by the types. The speed is noticeable has not changed (the operation was performed once per pack),
  but the position is now published after recording data,
  closing recipient in the middle of sending more does not leave a hole in the ring.

- **Blocking wait finally checked.** Path sender
  fell asleep, the recipient is obliged to wake him up, went into system calls,
  invisible for verification, parking is transferred to the interlayer, and the model is brute force all orders of execution proves that those who fall asleep are always woken up.
  The memory barrier on which this property rests has also come under check, 
  remove it -> The model finds a hang.

- **Waiting in blocking `send`/`recv` is guarded.** Queue node
  the wait lives on the stack, and panic through the wait would leave it on the list hanging sign. There is no accessible way there, but now it cannot appear,
  in the normal way it costs nothing.

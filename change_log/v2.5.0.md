## [2.5.0]

### Fixed

- **Batch operations woke only one waiter.** A batch receive that freed N
  slots, or a batch send that stored N items, called the wakeup once. The
  other waiters slept forever (measured: 4 slots free, only 1 of 3 parked
  senders woken). Batch paths now wake up to N waiters. When the wait queues
  are empty the cost is the same as before: one fence and two loads.

- **`recv_any` ate a wakeup that belonged to another waiter.** When it
  returned with an item from one shard, it silently removed its wait entries
  from the other shards, together with a wakeup that could belong to the
  waiter behind it. That waiter slept forever even with an item sitting in
  its shard. Now the return path passes the wakeup along, exactly like
  cancellation already did.

- **`recv_any` could park forever when racing with a close.** The check that
  all senders are gone ran only before the wait entries were registered. If
  the close finished inside that window, nobody was left to wake the
  entries. The check now runs again after registration, the same way the
  single shard receive does. Locked in with a race test of 400 iterations.

- **`ShardGroup::send_batch_timeout` destroyed the whole batch on a large
  timeout.** The deadline was computed AFTER the batch was split into local
  groups, and the overflow of `Instant + Duration::MAX` dropped every item
  during the unwind. The deadline is now computed before the split,
  and that addition can no longer overflow nywhere in the crate:
  deadline too large to represent means "no deadline", which is the state the wait loops already had.
 

- **A panicking `Drop` of an item killed a pool worker forever.** The item
  was dropped outside the panic catcher. The worker unwound, its shard was
  orphaned, and `wait_stopping()` hung forever. The item drop now runs under
  the same catcher as the handler.

- **The `mpmc!`/`spsc!` macros did not compile in other crates.**
  `::num_cpus` inside a macro resolves in the caller's crate. Without that
  crate's own `num_cpus` dependency the auto shard forms failed with E0433.
  The macros now go through a hidden reexport. Verified by building an
  external crate.

- **The pool could not be removed from the build.** The
  `#[cfg(feature = "pool")]` attribute was commented out, so the module was
  always compiled. The attribute is back: without the `pool` feature there
  is no module (verified with an external crate). If you use the pool, add
  `features = ["pool"]`.

- **`Config` is protected from extreme values.** The worker count is capped
  by the shard count. This is not an invented number but a property of the
  protocol: a shard has exactly one owner, so a worker beyond the shard
  count can never get work and only burns CPU. This also defuses absurd
  configs: `usize::MAX` used to be a fork bomb (overflow in debug, thread
  spawning until the machine died in release). `sample_interval` is clamped
  to at least 1 ms, because zero turned the monitor into a loop with no
  await point at all and wedged a single threaded runtime.

- **A pool with zero shards could never be stopped.** The auto drain never
  fired. The constructors now panic loudly on an empty receiver vector.

- **`try_send_batch` did not try every shard.** The first full shard aborted
  the call: three empty shards were never touched, and one slow consumer
  stalled every other key group (measured: sent = 0 before, sent = 3 after).
  All shards are now attempted. The first error is returned after the pass,
  and the buffer keeps only the items of the failed shards.

- **`try_recv_any` / `try_recv_batch_any` now report disconnection.**
  Before, "everything is empty" and "all senders are gone" looked the same,
  and the documented polling loop spun at 100% CPU forever. The first now
  returns an error when every shard is closed and drained. The second
  reports a disconnect flag, following the batch receive convention.

- **Errors became real errors.** No public error type implemented `Display`
  and `std::error::Error`, so a plain `?` into `Box<dyn Error>`/anyhow and
  `{}` in logs simply did not compile. All types now implement both, the
  messages are human readable, and the payload is still reachable through
  `into_inner()`.

- **The SPSC halves can be named from outside.** `take_pair` from the docs
  returned types from a private module: you could call methods but could not
  store them in a struct field. `SingleSender`/`SingleReceiver` (and
  `Sender`) are reexported from `channel`.

- **An out of range shard index now panics,** like slice indexing, with a
  clear message. Before, `try_recv(7)` on four shards silently read shard 3,
  handing the consumer another key group's data, and the `shard` field in
  the error showed the already wrapped index. For an untrusted index there
  is a non panicking twin in the style of `slice::get`:
  `get_receiver(shard) -> Option<..>`, and through it every per shard
  operation is available in `Result` form.

- **`Config::new(8, 2)` no longer raises the ceiling silently.** The ceiling
  is the hard promise: instead of raising max to 8, min is lowered to 2.

- **Cancelled wait entries no longer pile up behind a live waiter.** Cleanup
  only ran from the head of the queue. One long lived `recv_async` plus
  receivers with timeouts on a quiet channel grew the queue without bound.
  When tombstones make up at least half of the queue, the whole queue is
  swept. This is free in the amortized sense: every step of the sweep was
  paid for by an earlier cancellation.

### Changed

- **Dropping the pool handle stops the workers.** Before, a plain
  `drop(pool)` detached the threads forever: no handle, no signal, and the
  workers kept the receivers alive and kept processing (measured: an item
  sent after the drop was still processed). Now the sync pool stops and
  joins the workers in `Drop`, and the async pool sets the stop flag, so the
  tasks exit within one idle cycle. The explicit
  `wait_stopping`/`stop_and_wait` work as before.

- **Pool workers are spawned lazily.** Before, the constructor created all
  `max_consumers` threads or tasks at once, and `min_consumers` only steered
  shard placement, so the extra workers spun in an idle loop forever. Now
  exactly `min_consumers` workers exist at start, the monitor spawns the
  missing ones when the load actually grows, and a worker retired after a
  scale down parks at the monitor tick pace instead of the 50 microsecond
  idle loop. Measured (8 shards, empty pool, 2 seconds idle): 0.08 s of CPU
  against 0.84 s, which is 10 times less idle burn. Observability:
  `worker_handles()` on both pool handles. Verified by mutation: with the
  top up disabled the regression test fails.

- **The round robin cursor moved to the loom layer.** A direct std atomic
  was invisible to the model checker.

- **Honest docs on `helper::batch`:** the async drain is not cancel
  safe (cancellation at an await drops the items already taken out and the
  accumulator), and the sink must return an empty vector, because it is
  allocation reuse and not a retry channel (locked in with a debug_assert).

- **`Padding` is 128 bytes on x86_64 too.** The adjacent line prefetcher on
  Intel/AMD pulls pairs of 64 byte lines, so a 64 byte separation of the
  counters was not enough.
